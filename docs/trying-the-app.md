# 第一轮自愿试用

这是一份准备执行的试用方案，**不是已经完成的用户研究或使用人数证明**。当前仅确认维护者本人使用；外部试用、设备验证和反馈结果都应在实际发生后记录。

第一轮可以邀请 3–5 名自愿参与、愿意尝试中文习惯记录的用户。这个人数只是控制首轮维护工作量的建议，不是申请条件，也不代表已经找到参与者。应用保持温和、不责备的语气，试用不考核参与者的宗教实践。

## 邀请之前

维护者先确认 [README](../README.md) 的公开 HTTPS 入口已可用，并完成生产版本的联网打开、离线刷新、页面导航、记录持久化和备份恢复检查。把实际测试过的浏览器与设备写清楚，不把自动化模拟的手机宽度写成真机测试。

让参与者先阅读[第一次使用](getting-started.md)。说明：参与自愿，可以随时停止；不需要注册应用账号；记录只存在自己的浏览器；试用可以全部使用虚构内容。不要要求截图或导出真实习惯记录。

## 参与者可以尝试什么

| 任务 | 建议操作 | 需要反馈的结果 |
| --- | --- | --- |
| 找到入口 | 从 README 打开应用，不接受维护者逐步引导 | 是否找到入口，是否明白记录保存在哪里 |
| 记录并返回 | 在“今日”填虚构内容，等待保存结束后刷新 | 是否保留，保存提示是否清楚 |
| 查看与切换 | 查看“本周”，保存一个虚构地点，再回到“今日” | 是否理解页面含义，是否有难找或难点的控件 |
| 带走记录 | 从设置导出备份，找到下载的 JSON 文件 | 是否完成，是否理解文件包含哪些内容 |
| 预览与取消 | 选择刚导出的文件，检查预览并取消 | 是否理解替换范围，取消后内容是否不变 |
| 恢复 | 仅在虚构数据环境，先导出当前内容，再确认恢复 | 是否完成，是否明白恢复不会合并、没有撤销 |
| 离线 | 联网打开并等待缓存后，断网刷新、切换页面并保存虚构记录 | 哪一步成功或失败，错误文字是什么 |
| 可选：安装 | 查找浏览器安装或“添加到主屏幕”入口 | 是否找到、是否能打开；无需为此修改系统设置 |

任务可跳过，未完成不等于使用者做错。完成后只需询问：哪一步最费解、什么信息缺失、有没有愿意继续使用的场景、最希望解决哪一个具体问题。不要追问真实礼拜、饮食或伙伴记录。

## 如何记录反馈

公开反馈使用 [试用反馈表](https://github.com/musa426/One-Step-Closer/issues/new?template=usability_feedback.md)。不愿公开反馈的参与者，可以通过双方已有且同意使用的渠道描述问题。维护者征得同意后，用虚构数据重现，再创建不含身份信息的 issue；不要把私聊原文、联系方式或可识别的截图直接复制到仓库。

每个问题保留这些信息就足够：

- 应用版本、测试日期、设备类别、操作系统、浏览器及版本，是否离线或已安装到主屏幕。
- 尝试的任务，结果为“完成”“需帮助”“未完成”或“跳过”。
- 可复现的步骤、预期与实际结果、已去除个人信息的错误文字。
- 是否由维护者独立复现，相关 issue、修复 PR 和实际验证结果。

公开记录可以写“某 Android 浏览器在恢复预览处无法继续”，不需要姓名、账号映射、精确地点或个人实践情况。参与者自行发布的 GitHub issue 会公开显示其账号，因此不能承诺这些 issue 完全匿名。

维护者若要整理汇总，只统计实际发生且得到同意的试用；区分人数、反馈条数和重复问题。把“未尝试”“无法复现”“仅模拟浏览器验证”与“已验证”分开。没有反馈时，如实写尚未收到外部反馈，不用测试脚本或自己创建的 issue 代替真实用户。

## 从反馈到下一次发布

优先处理记录丢失风险、无法打开、无法保存和无法恢复；再处理主要任务中的操作困难。用最小的虚构用例复现问题，修复后补适当的回归检查，并在 issue 中说明结果。尚未复现的问题先记录不确定性，不承诺已解决。

发布说明只写实际合并的改变和实际完成的验证。邀请参与者复查其遇到的问题时仍须征得同意，不要求持续试用。维护流程见 [维护指南](maintaining.md)，版本变化记在 [CHANGELOG](../CHANGELOG.md)。
